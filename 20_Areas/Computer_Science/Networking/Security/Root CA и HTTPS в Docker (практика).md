# Свой Центр Сертификации (CA) и Настройка HTTPS в Docker

Эта заметка содержит полное руководство по созданию собственного локального Центра Сертификации (Root CA), генерации SSL/TLS сертификатов для веб-серверов с поддержкой расширений SAN (Subject Alternative Name) и развертыванию защищенного контейнера Nginx.

## Теоретический фундамент [[TLS и SSL — Сравнение и история версий|TLS/SSL: теория]]

Перед началом работы важно понимать три ключевых этапа создания цепочки доверия (**Chain of Trust**):

1. **Приватный Ключ (`.key`)** — это секретная цифровая подпись. Тот, кто владеет этим ключом, может шифровать данные или подписывать документы от своего имени. Его нельзя никому передавать.
2. **Запрос на подпись (`.csr` / Certificate Signing Request)** — это «заявление» на получение паспорта. Содержит открытый (публичный) ключ и метаданные (домен, страну, компанию). Печатей на нем еще нет.
3. **Сертификат (`.crt`)** — это готовый «паспорт», подписанный доверенным лицом (CA). Его проверяют клиенты (браузеры, утилиты вроде `curl`).

##  Практическая реализация (Пошагово)
### Шаг 1: Создание собственного Root CA
Мы берем на себя роль доверенного Центра Сертификации. Все наши будущие сертификаты будут доверять этому корневому узлу.

**1. Генерация приватного ключа для CA:**
```bash
openssl genrsa -out rootCA.key 2048
```

- `genrsa` — использовать алгоритм RSA.
- `-out rootCA.key` — имя выходного файла секретного ключа.
- `2048` — длина ключа в битах (стандарт безопасной стойкости).

**2. Создание самоподписного корневого сертификата:**

```bash
openssl req -x509 -new -nodes -key rootCA.key -sha256 -days 365 -out rootCA.crt \
  -subj "/C=UZ/L=Tashkent/O=MyLocalLab/CN=My Root CA"
```

- `-x509` — флаг, который говорит создать _готовый самоподписной сертификат_, а не запрос (CSR).
- `-nodes` — (no DES) не шифровать приватный ключ паролем (удобно для локальных лаб).
- `-sha256` — алгоритм хэширования для подписи.
- `-days 365` — срок действия сертификата (1 год).
- `-subj` — автоматическое заполнение полей субъекта (C — страна, L — город, O — организация, CN — Common Name / Имя ЦА).

### Шаг 2: Создание сертификата для сервера (Nginx)

Теперь мы выступаем в роли администраторов сайта `localhost` (или любого другого домена), которым нужно защитить трафик.

**1. Генерация приватного ключа сервера:**

```bash
openssl genrsa -out server.key 2048
```

- Создает уникальный закрытый ключ `server.key` именно для нашего веб-сервера.

**2. Создание запроса на подпись (CSR):**
```bash
openssl req -new -key server.key -out server.csr \
  -subj "/C=UZ/L=Tashkent/O=DevOpsApp/CN=localhost"
```

- `-new` — создать новый запрос.
- `CN=localhost` — критически важное поле. Имя должно строго совпадать с доменом, по которому мы будем обращаться к серверу.

**3. Создание файла конфигурации расширений (`server.ext`):**

Современные браузеры и компоненты (включая Kubernetes) отбраковывают сертификаты, если в них нет расширения **SAN (Subject Alternative Name)**.
Создай локально файл `server.ext`:

```toml
authorityKeyIdentifier=keyid,issuer
basicConstraints=CA:FALSE
keyUsage = digitalSignature, nonRepudiation, keyEncipherment, dataEncipherment
subjectAltName = @alt_names

[alt_names]
DNS.1 = localhost
IP.1 = 127.0.0.1
```

- `basicConstraints=CA:FALSE` — указывает, что данный сертификат конечный и сам не может подписывать другие сертификаты.
- `subjectAltName` — указывает альтернативные имена (домены и IP), для которых этот сертификат будет считаться валидным.

**4. Подпись серверного запроса с помощью Root CA:**
```bash
openssl x509 -req -in server.csr -CA rootCA.crt -CAkey rootCA.key \
  -CAcreateserial -out server.crt -days 365 -sha256 -extfile server.ext
```

- `x509` — утилита для работы с сертификатами X.509.
- `-req -in server.csr` — подаем на вход созданное ранее «заявление» сервера.
- `-CA rootCA.crt -CAkey rootCA.key` — указываем, _кто_ подписывает (наш корневой сертификат и его секретный ключ).
- `-CAcreateserial` — создает файл с серийным номером для отслеживания выданных сертификатов.
- `-extfile server.ext` — подмешивает настройки SAN в финальный файл.

На выходе получаем валидный **`server.crt`**.

### Шаг 3: Развертывание в Docker (Nginx)

**1. Конфигурационный файл `nginx.conf`:**

Создай файл конфигурации для Nginx, который включает SSL и указывает пути к файлам в корне папки конфигов:

```nginx
events {}

http {
    server {
        listen 443 ssl;
        server_name localhost;

        # Пути внутри контейнера
        ssl_certificate /etc/nginx/server.crt;
        ssl_certificate_key /etc/nginx/server.key;

        ssl_protocols TLSv1.2 TLSv1.3;

        location / {
            root /usr/share/nginx/html;
            index index.html;
        }
    }
}
```

**2. Запуск контейнера в Docker:**

Убедись, что старый контейнер удален (`docker rm -f secure-web`), и выполни:

```bash
docker run -d \
  --name secure-web \
  -p 443:443 \
  -v $(pwd)/nginx.conf:/etc/nginx/nginx.conf:ro \
  -v $(pwd)/server.crt:/etc/nginx/server.crt:ro \
  -v $(pwd)/server.key:/etc/nginx/server.key:ro \
  nginx:alpine
```

- `-p 443:443` — проброс защищенного порта наружу.
- `-v ...:/etc/nginx/...:ro` — монтирование файлов в режиме "только чтение" (`ro`). Мы кладем их в корень `/etc/nginx/`, так как подпапки `ssl` в дефолтном образе не существует, что предотвращает ошибку старта `BIO_new_file() failed`.

## Верификация и Отладка

### Одноразовая проверка (curl)

Если выполнить `curl https://localhost`, утилита вернет ошибку, так как она не знает нашего издателя. Чтобы принудительно скормить утилите наш Root CA, используем флаг `--cacert`:

```bash
curl --cacert rootCA.crt https://localhost
```

### Добавление Root CA в доверенные (Arch Linux / Браузеры)

Чтобы браузеры на твоей машине не выдавали предупреждений безопасности и показывали "заветный замок", систему нужно принудительно подружить с созданным Root CA:

1. Копируем сертификат в системное хранилище доверенных источников:
    
    ```bash
    sudo cp rootCA.crt /etc/ca-certificates/trust-source/anchors/myLocalRootCA.crt
    ```
    
2. Обновляем базу данных сертификатов ОС:
    
    ```bash
    sudo update-ca-trust
    ```
    
3. Полностью перезапускаем браузер.
