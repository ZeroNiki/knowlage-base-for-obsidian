# Пошаговое практическое руководство: Установка и базовая эксплуатация Argo CD в Kubernetes

Argo CD — это декларативный Kubernetes-native инструмент непрерывной доставки (CD), ставший индустриальным стандартом благодаря реализации модели GitOps. Его стратегическая важность заключается в использовании pull-based модели: контроллер Argo CD, работая внутри кластера, самостоятельно забирает изменения из Git. Это исключает необходимость передачи учетных данных кластера во внешние CI-системы, создавая максимально защищенный периметр безопасности и обеспечивая соответствие живого состояния среды (live state) желаемому (desired state).

---

## 1. Подготовка и развертывание Argo CD

Argo CD интегрируется непосредственно в экосистему Kubernetes, расширяя ее возможности через Custom Resource Definitions (CRD) и специализированные контроллеры.

### 1.1. Системные требования и создание окружения
Для работы требуется кластер Kubernetes и настроенный kubectl. Первым шагом подготовим изолированное пространство имен.

```bash
kubectl create namespace argocd
```

### 1.2. Процесс установки через официальные манифесты

Развертывание выполняется путем применения манифеста стабильной версии.

```bash
kubectl apply -n argocd --server-side --force-conflicts -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
```

> [!NOTE]
> **Важное уточнение:** Использование флагов `--server-side` и `--force-conflicts` является критически важным. Это связано с ограничениями Kubernetes на размер CRD Argo CD: схемы данных настолько объемны, что стандартная проверка на стороне клиента может завершиться ошибкой.

> [!IMPORTANT]
> **Аналитический слой "So What?":** Использование декларативных манифестов для установки самого Argo CD обеспечивает предсказуемость состояния управляющего слоя. Это позволяет восстановить всю систему CD из Git в случае катастрофического сбоя, гарантируя воспроизводимость инфраструктуры управления.

### 1.3. Верификация статуса компонентов

Убедитесь, что все системные поды запущены корректно. Ключевые компоненты:

* `argocd-server`: API-сервер, выступающий единственной точкой входа для Web UI, CLI и внешних систем (REST/gRPC).
* `argocd-repo-server`: Внутренний сервис, отвечающий за клонирование Git-репозиториев и рендеринг манифестов (преобразование Helm-чартов или Kustomize-шаблонов в чистый YAML).
* `argocd-application-controller`: «Сердце» системы. Контроллер, который непрерывно сравнивает состояние кластера с Git и инициирует синхронизацию.

Проверить статус можно командой:

```bash
kubectl get pods -n argocd
```

Успешное развертывание компонентов позволяет перейти к настройке интерфейсов управления.

## 2. Доступ к управлению и авторизация

Разделение интерфейсов управления — Web UI для визуализации топологии ресурсов и CLI для автоматизации — позволяет эффективно совмещать мониторинг с операционной деятельностью.

### 2.1. Проброс портов (Port-Forwarding) для Web UI

Для базовой настройки без конфигурирования Ingress используйте механизм Port-Forward:

```bash
kubectl port-forward svc/argocd-server -n argocd 8080:443
```

Интерфейс станет доступен по адресу **`https://localhost:8080`**.

### 2.2. Извлечение начального пароля администратора

Начальный пароль генерируется автоматически и хранится в секрете. Извлеките его с помощью декодирования base64:

```bash
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d
```

> [!WARNING]
> **Безопасность:** Рекомендуется сменить этот пароль немедленно после первого входа в систему через настройки пользователя.

### 2.3. Настройка и аутентификация через CLI

CLI необходим для интеграции в CI/CD пайплайны и быстрой диагностики. Авторизуйтесь командой:

```bash
argocd login localhost:8080
```

> [!IMPORTANT]
> **Аналитический слой "So What?":** Если GUI идеален для визуального контроля здоровья приложения, то CLI — это инструмент инженера для повседневных задач и автоматизации. Знание CLI позволяет переносить рутинные операции в скрипты, превращая управление доставкой в "GitOps-as-Code".

Теперь, когда доступ к системе настроен, мы переходим к созданию первой декларативной единицы развертывания — объекта Application.

## 3. Декларативный деплой: Объект Application

Объект Application (Custom Resource) является «мостом», связывающим конкретный Git-репозиторий с целевым пространством имен в кластере.

### 3.1. Анатомия манифеста Application

Манифест определяет, что, откуда и куда деплоить.

| Секция | Описание | Пример значения |
| --- | --- | --- |
| **Source** | Источник истины (Git) | `repoURL`, `path`, `targetRevision: head` (последний коммит) |
| **Destination** | Целевой кластер и Namespace | `https://kubernetes.default.svc`, `namespace: prod` |
| **Project** | Группировка для RBAC | `default` |

### 3.2. Политики синхронизации и самоисцеления

Секция `syncPolicy` определяет уровень автоматизации:

* `automated`: Автоматическое применение изменений при их появлении в Git.
* `prune`: Удаление ресурсов из кластера, если они исчезли из Git.
* `selfHeal`: Автоматический откат любых ручных изменений в кластере, сделанных в обход Git.
* `CreateNamespace=true`: Опция, позволяющая Argo CD самостоятельно создавать целевой namespace, если он отсутствует.

> [!IMPORTANT]
> **Аналитический слой "So What?":** Опция `selfHeal` критична для Production-сред. Она полностью исключает человеческий фактор и "configuration drift" (дрейф конфигурации), делая Git единственным источником истины. Любая попытка ручного исправления `kubectl edit` будет мгновенно подавлена контроллером.

### 3.3. Применение манифеста

Примените созданный YAML-файл через стандартный kubectl:

```bash
kubectl apply -f my-app.yaml -n argocd
```

После успешного деплоя управление жизненным циклом приложения переходит в фазу активной эксплуатации и мониторинга.

## 4. Повседневная эксплуатация и мониторинг через CLI

Владение CLI-инструментарием позволяет инженеру мгновенно диагностировать состояние системы и управлять жизненным циклом приложений.

### 4.1. Мониторинг состояния приложений

Используйте команды `argocd app list` и `argocd app get <name>` для оценки статуса.

| Статус | Описание | Возможные значения |
| --- | --- | --- |
| **Sync Status** | Соответствие манифестов Git и кластера | `Synced`, `OutOfSync` |
| **Health Status** | Работоспособность ресурсов (подов) | `Healthy`, `Degraded`, `Progressing` |

### 4.2. Ручное управление синхронизацией и откат (Rollback)

Если автосинхронизация отключена, используйте:

```bash
argocd app sync <app-name>
```

В случае критической ошибки Argo CD позволяет выполнить мгновенный откат:

```bash
argocd app rollback <app-name>
```

> [!IMPORTANT]
> **Аналитический слой "So What?":** Функция Rollback в Argo CD значительно мощнее стандартного `kubectl rollout`. Она позволяет откатиться на любую зафиксированную в Git конфигурацию, включая не только версии образов, но и связанные с ними ConfigMap, Service и права доступа (RBAC).

### 4.3. Базовая диагностика

Для выявления причин ошибок синхронизации или проблем в работе приложения используйте просмотр событий и логов:

```bash
argocd app logs <app-name>
argocd app events <app-name>
```

Внедрение Argo CD трансформирует процесс доставки ПО из цепочки ручных манипуляций в прозрачный, аудируемый и полностью автоматизированный поток, обеспечивая высочайший уровень стабильности инфраструктуры.
