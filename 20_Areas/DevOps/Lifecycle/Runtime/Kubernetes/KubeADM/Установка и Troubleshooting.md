# KUBEADM: Установка и Troubleshooting

## About
> [!info] About
> **Kubeadm** — это инструмент, разработанный для предоставления команд `kubeadm init` и `kubeadm join` в качестве «быстрых путей» в соответствии с передовыми практиками для создания кластеров Kubernetes. **kubeadm** выполняет действия, необходимые для запуска и работы минимально жизнеспособного кластера. По замыслу, он занимается только начальной настройкой, а не подготовкой машин. Аналогично, установка различных дополнительных компонентов, таких как Kubernetes Dashboard, решения для мониторинга и дополнения, специфичные для конкретных облачных платформ, не входит в сферу его применения.

Вот полный список команд, которые мы использовали для настройки системы, подготовки окружения, инициализации кластера и устранения проблем, с подробными пояснениями для каждого шага.

### 1. Подготовка системы (выполняется на обеих нодах через Vagrant Provision / init.sh)

* **Отключение SWAP:**
```bash
swapoff -a
sed -i '/ swap / s/^/#/' /etc/fstab
```


*Пояснение:* Kubernetes требует обязательного отключения подкачки (swap), чтобы корректно планировать ресурсы памяти для подов.
* **Загрузка модулей ядра для сетевого фильтра:**
```bash
cat <<EOF | tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF

modprobe overlay
modprobe br_netfilter

```


*Пояснение:* Модули `overlay` и `br_netfilter` необходимы для работы контейнеризатора и корректной фильтрации сетевого трафика через мосты (нужно для `kube-proxy` и сетевых плагинов).
* **Включение форвардинга пакетов IP:**
```bash
cat <<EOF | tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF

sysctl --system
```


*Пояснение:* Настройка параметров ядра Linux для того, чтобы пакеты между подами корректно маршрутизировались через iptables.

### 2. Инициализация Master-ноды (`k8s-master`)

* **Инициализация кластера (Kubeadm):**
```bash
sudo kubeadm init --apiserver-advertise-address=192.168.56.10 --pod-network-cidr=10.244.0.0/16
```

*Пояснение:* Запускает control-plane. Флаг `--apiserver-advertise-address` жестко привязывает API-сервер к IP-адресу внутренней сети VirtualBox (`eth1`), а `--pod-network-cidr` задает подсеть для внутренних подов (нужно для Flannel).
* **Настройка `kubectl` для текущего пользователя:**
```bash
mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config
```

*Пояснение:* Копирует конфигурационный файл администратора в домашнюю директорию, чтобы утилита `kubectl` могла подключаться к кластеру.
* **Установка сетевого плагина (Flannel):**
```bash
curl -O https://raw.githubusercontent.com/coreos/flannel/master/Documentation/kube-flannel.yml
kubectl apply -f kube-flannel.yml
```
- отредактировать добавив --iface=eth1 (если это виртуалка)


*Пояснение:* Развертывает сетевой плагин, который создает виртуальную сеть между всеми нодами кластера, чтобы поды могли общаться друг с другом.

---

### 3. Подключение Worker-ноды (`k8s-worker`)

* **Присоединение воркера к кластеру:**
```bash
sudo kubeadm join 192.168.56.10:6443 --token <token> --discovery-token-ca-cert-hash sha256:<hash>
```

*Пояснение:* Команда генерируется на мастере при инициализации. Она авторизует рабочую ноду в кластере с помощью токена и хэша сертификата безопасности.

### 4. Диагностика и Troubleshooting (устранение проблем)

* **Проверка состояния нод:**
```bash
kubectl get nodes
```

*Пояснение:* Выводит список всех нод в кластере и их статус (`Ready` или `NotReady`).
* **Проверка состояния всех подов (включая системные):**
```bash
kubectl get pods --all-namespaces -o wide
```

*Пояснение:* Позволяет увидеть, на каких нодах запущены системные поды (CoreDNS, Flannel, kube-proxy) и каков их статус.
* **Просмотр логов службы `kubelet`:**
```bash
sudo journalctl -xeu kubelet
```

*Пояснение:* Главный инструмент отладки агента Kubernetes на ноде. Помогает увидеть ошибки регистрации ноды или проблемы с рантаймом контейнеров.
* **Сброс состояния кластера (при сбоях):**
```bash
sudo kubeadm reset -f
```

*Пояснение:* Полностью откатывает изменения, сделанные `kubeadm` на ноде, удаляет старые сертификаты и конфигурации для возможности повторного подключения.
* **Очистка сетевого «мусора» CNI:**
```bash
sudo ip link delete cni0 2>/dev/null || true
sudo ip link delete flannel.1 2>/dev/null || true
sudo rm -rf /etc/cni/net.d /var/lib/cni/
```

*Пояснение:* Удаляет зависшие виртуальные сетевые мосты и кэш старых конфигураций сети, которые часто блокируют поднятие новых подов после сброса кластера.
* **Перезапуск рантайма и kubelet:**
```bash
sudo systemctl restart containerd
sudo systemctl restart kubelet
```

*Пояснение:* Перезапускает контейнеризатор (`containerd`) и агент ноды для применения чистых сетевых настроек.

## Troubleshooting
### Problem
* Воркер-нода зависала в статусе `NotReady` из-за ошибок сети (`Container runtime network not ready` и сбоев создания песочниц в `containerd`).
* Сетевой плагин Flannel по умолчанию выбирал не тот интерфейс (пытался работать через `eth0` с NAT вместо внутренней сети VirtualBox `192.168.56.x`).
* При попытках выполнять команды на воркере возникала ошибка подключения к `localhost:8080`, так как управление кластером должно производиться исключительно с мастер-ноды.
* При попытках исправить ситуацию на лету в системе накопился сетевой «мусор» (старые мосты `cni0`, `flannel.1` и кэш CNI).

### Resolution
* **Полный сброс:** На обеих нодах выполнен `kubeadm reset` для удаления старых сертификатов и конфигураций.
* **Очистка сети CNI:** Удалены зависшие виртуальные интерфейсы (`sudo ip link delete cni0`, `sudo ip link delete flannel.1`) и очищены директории `/etc/cni/net.d` и `/var/lib/cni/`.
* **Правильная инициализация:** Мастер запущен заново с явной привязкой к частной сети VirtualBox (`--apiserver-advertise-address=192.168.56.10`).
* **Настройка интерфейса Flannel:** В манифест Flannel добавлен параметр `--iface=eth1`, чтобы трафик гарантированно шел через внутреннюю сеть виртуалкок.
* **Переподключение:** Воркер успешно подключен по новому токену, а все административные команды `kubectl` стали выполняться с мастер-ноды.

### Postmortem

* **Контроль интерфейсов:** В средах виртуализации (VirtualBox, VMware) с несколькими сетевыми адаптерами всегда нужно явно указывать интерфейсы для control-plane и CNI-плагинов, чтобы избежать конфликтов маршрутизации.
* **Чистота сброса:** Команда `kubeadm reset` убирает не все артефакты сети. При пересоздании кластера обязательно нужно вручную удалять мосты `cni0` и очищать `/etc/cni/net.d`.
* **Разделение ролей:** Воркер-ноды не содержат API-сервер, поэтому любые диагностические и управляющие команды (`kubectl`) выполняются исключительно на мастер-ноде.
