# Стандарты безопасности, аудит, анализ угроз и шифрование данных в Kubernetes (Security Standards, Threat Analysis & Data Protection)

---

## 1. Блок 1. Теория простыми словами

### 1.1. Бенчмарки безопасности и анализ уязвимостей (CIS Benchmarks & OWASP K8s Top 10)

Стандартизация конфигураций безопасности и систематический анализ уязвимостей представляют собой незыблемый фундамент защиты cloud-native инфраструктуры. В масштабируемых и динамических средах Kubernetes автоматизированная проверка настроек компонентов Control Plane, узлов и рабочих нагрузок критически важна для предотвращения конфигурационного дрейфа, соответствия отраслевым стандартам (PCI-DSS, ISO 27001, SOC 2) и успешного прохождения аудитов compliance. Без четких эталонов конфигурации инфраструктура неизбежно превращается в хаотичную среду с массой скрытых векторов атак.

#### CIS Kubernetes Benchmarks

Основным мировым стандартом для защиты Kubernetes является **Center for Internet Security (CIS) Kubernetes Benchmark** — вендоронезависимое руководство по жесткому конфигурированию (*hardening*) кластеров. Документ регулярно обновляется экспертным сообществом и охватывает как ванильный Kubernetes (версии 1.28–1.31+), так и управляемые облачные сервисы (Amazon EKS, Azure AKS, Google GKE, Red Hat OpenShift).

Структура CIS Benchmark разделена на четыре ключевые секции:

1. **Control Plane Components**: Настройки API-сервера (`kube-apiserver`), контроллер-менеджера (`kube-controller-manager`), планировщика (`kube-scheduler`) и конфигурационных файлов PKI/kubeconfig.
2. **etcd**: Ограничение доступа, проверка сертификатов mTLS, владельцев файлов баз данных и ключей.
3. **Worker Nodes**: Конфигурация службы `kubelet`, параметры файловой системы, аутентификация и авторизация на нодах.
4. **Policies & SecurityContext**: Правила RBAC, настройки пространств имен, селекторы и ограничения контейнеров.

Для автоматической проверки кластера на соответствие CIS Benchmark применяется де-факто стандарт индустрии — утилита **`kube-bench`** от компании Aqua Security. Инструмент запускается как консольная утилита на узлах или внутри кластера в виде Job/DaemonSet, сканирует конфигурационные файлы и параметры процессов, после чего выдает детальный статус по каждому пункту (`PASS`, `FAIL`, `WARN`).

| Компонент кластера | Проверяемый параметр CIS | Потенциальный риск при несоблюдении |
| --- | --- | --- |
| **Control Plane (API Server)** | Проверка TLS-параметров (`--tls-cert-file`, `--tls-private-key-file`), отключение анонимного доступа (`--anonymous-auth=false`), закрытие незащищенного порта. | Перехват трафика, несанкционированный доступ к API, атаки Man-in-the-Middle (MitM). |
| **etcd Storage** | Использование mTLS (`--cert-file`, `--key-file`, `--trusted-ca-file`), разграничение прав на `/var/lib/etcd` (`600`/`root:root`). | Прямая кража базы данных etcd с извлечением всех секретов и токенов кластера. |
| **Worker Nodes (Kubelet)** | Запрет анонимного доступа (`--anonymous-auth=false`), включение Webhook-авторизации, настройка `readOnlyPort=0`. | Выполнение произвольного кода на ноде через незащищенный порт Kubelet (`10250`/`10255`). |
| **Policies / SecurityContext** | Ограничение привилегий (`runAsUser != 0`, `allowPrivilegeEscalation: false`, блокировка `CAP_SYS_ADMIN`). | Побег из контейнера и захват прав суперпользователя на хостовой операционной системе. |

#### OWASP Kubernetes Top 10

Проект OWASP классифицирует наиболее критические риски безопасности кластеров. Детальный анализ пяти главных векторов атак включает:

1. **Misconfigurations (Ошибки конфигурации)**: Использование параметров по умолчанию, небезопасные сетевые политики (*Default Allow*), отсутствие лимитов ресурсов (*Resource Quotas*) и запуск процессов с первичной группой root (`gid=0` при отсутствии `runAsGroup`).
2. **RBAC Abuse (Злоупотребление правами доступа)**: Предоставление избыточных прав сервисным учетным записям (*ServiceAccounts*) или пользователям. Атаки через разрешения asterisk (`*`) на ресурсы `pods/exec`, `secrets` или `roles/bind`.
3. **Secrets Leakage (Утечка секретов)**: Хранение чувствительных данных (пароли, API-ключи, сертификаты) в открытом виде в Git-репозиториях, кодирование в base64 без шифрования в etcd, переменные окружения контейнеров или логи приложений.
4. **Over-privileged Containers (Избыточные привилегии контейнеров)**: Запуск контейнеров с флагом `privileged: true`, флагом `allowPrivilegeEscalation: true` или с опасными Linux Capabilities (`CAP_SYS_ADMIN`, `CAP_NET_ADMIN`, `CAP_SYS_PTRACE`).
5. **Supply Chain Attacks (Атаки на цепочку поставок)**: Использование необразмеренных (*unpinned*) или уязвимых базовых образов контейнеров из публичных реестров, отсутствие проверки цифровых подписей (Cosign/Notary) и запуск процессов от имени пользователей, определенных в `/etc/group` образа.

> [!tip] Рекомендация для экзамена CKS
> При сдаче CKS вы должны уметь быстро запускать `kube-bench` для конкретных узлов, находить упавшие проверки (статус `FAIL`) и оперативно править манифесты статических подов в `/etc/kubernetes/manifests/` (API Server, Controller Manager, Scheduler, etcd) или конфигурацию Kubelet `/var/lib/kubelet/config.yaml`.

### 1.2. Векторы атак, побег из контейнера и эскалация привилегий

Концепция **Defense in Depth** (глубокоэшелонированная защита) исходит из реалистичной предпосылки: внешняя оболочка любого приложения рано или поздно будет пробита через RCE или уязвимость нулевого дня. В этот момент ключевой задачей безопасности становится максимальное сужение радиуса поражения (*blast radius*) и предотвращение выхода атакующего за пределы контейнера на хостовую ноду.

#### Матрица атак и пошаговый сценарий компрометации (MITRE ATT&CK)

Атака на кластер Kubernetes в рамках матрицы MITRE ATT&CK for Containers обычно развивается по следующей цепочке:

```
[RCE в приложении] ──> [Разведка окружения (/proc, SA token)] ──> [Эскалация прав в контейнере]
                                                                          │
[Захват Control Plane] <── [Атака на API-сервер через RBAC] <── [Побег на хостовую ноду]

```

1. **Initial Access & Execution**: Эксплуатация RCE в веб-приложении (например, через уязвимый библиотечный компонент) и получение интерактивной оболочки (*Reverse Shell*).
2. **Discovery**: Проверка битовой маски системных вызовов через `/proc/1/status` (поля `CapPrm`, `CapEff`), чтение файлов токенов `/var/run/secrets/kubernetes.io/serviceaccount/token` и сканирование внутренней сети Pod CIDR.
3. **Privilege Escalation**: Использование уязвимых setuid-бинарников внутри контейнера, если не установлен флаг ядра `no_new_privs` (`allowPrivilegeEscalation: true`).
4. **Container Escape**: Выход на хостовую ноду за счет прямого доступа к сокету среды исполнения (`containerd.sock`), монтирования чувствительных путей `/proc` или использования флага `--privileged`.
5. **Persistence & Lateral Movement**: Извлечение учетных данных Kubelet, чтение конфигураций `kubeconfig` на хосте и захват контроля над всеми узлами кластера через API-сервер.

#### Побег из контейнера (Container Escape) и методы блокировки

Выход из контейнера возможен из-за ослабления или некорректной настройки изоляции на уровне ядра Linux. Ниже приведены ключевые векторы риска и способы их закрытия через `SecurityContext`:

| Фактор риска / Вектор | Механика угрозы | Мера противодействия в SecurityContext |
| --- | --- | --- |
| **Флаг `--privileged**` | Снятие всех ограничений cgroups/namespaces, предоставление контейнеру всех capabilities и прямого доступа к устройствам `/dev`. | Запрет флага `privileged: false`. Использование правил Pod Security Standards (профиль Restricted). |
| **Монтирование сокетов (`containerd.sock`)** | Получение прямого управления движком контейнеризации. Атакующий запускает новый контейнер с монтированием `/` хоста. | Запрет монтирования `hostPath` с сокетами через Admission Controllers (ValidatingAdmissionPolicy / Kyverno). |
| **Privilege Escalation** | Допуск смены UID через setuid/setgid-бинарники (`no_new_privs` равен `false`). | Обязательное указание `allowPrivilegeEscalation: false`. |
| **Избыточные Capabilities** | Предоставление опасных привилегий ядра (`CAP_SYS_ADMIN`, `CAP_NET_ADMIN`, `CAP_SYS_PTRACE`, `CAP_DAC_READ_SEARCH`). | Явный сброс всех прав с точечным добавлением: `capabilities: { drop: ["ALL"], add: ["NET_BIND_SERVICE"] }`. |
| **Доступ к `/proc` и `/sys**` | По умолчанию runtime маскирует опасные пути (`/proc/kcore`, `/sys/firmware`). При `procMount: Unmasked` маскирование снимается. | Использование `procMount: Default`. Режим `procMount: Unmasked` требует обязательного применения User Namespaces (`spec.hostUsers: false`). |
| **Неограниченные sys-вызовы** | Доступ процессов к полному набору системных вызовов ядра хоста. | Ограничение системных вызовов через Seccomp (`seccompProfile: { type: RuntimeDefault }`). |

#### Эскалация привилегий через ServiceAccount и подмену идентификаторов

Сервисные учетные записи (*ServiceAccount*) по умолчанию монтируют JWT-токен в директорию `/var/run/secrets/kubernetes.io/serviceaccount`. Если сервисной учетной записи через RBAC RoleBinding были непреднамеренно выданы права на создание Подов (`pods/create`), просмотр Секретов (`secrets/get`, `list`) или выполнение команд (`pods/exec`), атакующий моментально поднимает привилегии до уровня администратора кластера (*cluster-admin*).

Дополнительный вектор угроз связан с идентификаторами процессов и объединением групп:

* **Root primary GID**: Если в `PodSecurityContext` указан `runAsUser: 1000`, но опущен `runAsGroup`, первичным GID процесса становится `0` (`root`). Это позволяет процессу модифицировать файлы, принадлежащие группе root.
* **Implicit `/etc/group` merges**: По умолчанию Kubernetes объединяет группы из Pod с группами из файла `/etc/group` базового образа (политика Merge). Если пользователь в образе входит в группу `50000`, эта группа автоматически добавится к процессу, что компрометирует разграничение прав на томах.
* **Решение (`SupplementalGroupsPolicy`)**: Фича `supplementalGroupsPolicy: Strict` (Beta с Kubernetes v1.33) гарантирует, что к процессу привязываются только явно указанные `fsGroup`, `supplementalGroups` и `runAsGroup`, полностью игнорируя содержимое `/etc/group` контейнера.

> [!danger] Критический риск privilege escalation и сокетов
> Предоставление контейнерам доступа к сокету среды исполнения (`/run/containerd/containerd.sock` или `/var/run/docker.sock`) равносильно предоставлению беспрепятственного root-доступа к хостовой ноде. Флаг `allowPrivilegeEscalation: false` является обязательным атрибутом любого манифеста и несовместим с `privileged: true` или наличием `CAP_SYS_ADMIN`.

### 1.3. Защита данных в покое (At Rest) и катастрофоустойчивость

Защита данных в покое и обеспечение катастрофоустойчивости (Disaster Recovery, DR) направлены на сохранение конфиденциальности, целостности и постоянной доступности состояния кластера. Потеря базы данных etcd или утечка ее содержимого эквивалентна полной компрометации и остановке всех бизнес-процессов организации.

#### Шифрование данных в etcd (EncryptionConfiguration)

По умолчанию Kubernetes хранит все объекты (включая Секреты — Secrets) в базе данных etcd в виде открытого JSON-текста. Кодирование значения секретов в base64 является исключительно форматом представления данных и не является мерой защиты. Любой субъект, получивший доступ к файлу базы данных etcd (`/var/lib/etcd`), бэкапу etcd или файловой системе Master-ноды, может моментально прочитать любые пароли, токены и приватные ключи.

Для защиты данных в покое применяется механизм `EncryptionConfiguration`. В конфигурационном файле задается цепочка провайдеров шифрования, которые обрабатывают данные при записи в etcd и чтении из него:

* **`aead/secretbox` / `aesgcm**`: Симметричные криптографические провайдеры (AES-GCM или Secretbox на базе Salsa20/Poly1305). Используют 32-байтовый ключ, закодированный в base64. Рекомендуются для локального шифрования.
* **`kms` (Key Management Service)**: Наиболее защищенный подход (*Envelope Encryption*). API-сервер использует внешний KMS (AWS KMS, GCP KMS, Azure Key Vault, HashiCorp Vault) для шифрования локального Data Encryption Key (DEK), которым зашифровываются секреты.
* **`identity`**: Провайдер-"пустышка", записывающий данные в открытом виде без шифрования.

**Критическое правило порядка провайдеров**: API-сервер использует **первый** провайдер в списке для записи новых секретов. Оставшиеся провайдеры используются для расшифровки ранее записанных данных.

```yaml
# ПРАВИЛЬНО: Новые данные шифруются через secretbox, старые могут читаться
providers:
  - secretbox: ...
  - identity: {}

# ОПАСНО: Новые данные будут писаться В ОТКРЫТОМ ВИДЕ!
providers:
  - identity: {}
  - secretbox: ...

```

#### Внешние хранилища секретов (ESO vs Secrets Store CSI Driver)

Хранение секретов внутри etcd даже с включенным шифрованием имеет недостаток: секреты попадают в память API-сервера и монтируются в виде обычных файлов/переменных окружения. Для Enterprise-инфраструктур применяются два архитектурных паттерна работы с внешними KMS (например, HashiCorp Vault):

* **External Secrets Operator (ESO)**: Kubernetes Operator, который синхронизирует секреты из внешнего хранилища (Vault, AWS Secrets Manager) в native Kubernetes Secret ресурсы. Приложение работает со стандартными секретами K8s.
* **Secrets Store CSI Driver**: Драйвер монтирует секреты из внешнего хранилища напрямую в файловую систему Пода в виде эфемерного тома (*volume*) без создания объекта Secret в базе etcd.

#### Резервное копирование и восстановление (etcdctl vs Velero)

Стратегия катастрофоустойчивости включает два уровня бэкапа:

1. **Низкоуровневый бэкап etcd (`etcdctl snapshot save`)**: Создание точного снимка всей базы данных etcd на уровне ключей и значений. Позволяет восстановить Control Plane с нуля при полной гибели мастер-нод.
2. **Высокоуровневый бэкап ресурсов и томов (Velero, Kasten K10)**: Создание бэкапов манифестов манипулированием API-сервера и снимков томов Persistent Volumes (PV) через CSI-снапшоты. Позволяет восстанавливать отдельные приложения или пространства имен.

> [!warning] Защита мастер-ключей и правильный порядок ротации (Key Rotation)
> Конфигурационный файл `/etc/kubernetes/enc/enc.yaml`, содержащий 32-байтовый мастер-ключ, должен иметь права доступа `600` и принадлежать `root:root`. При ротации ключей новый ключ добавляется **НАВЕРХ** списка провайдеров, выполняется команда перезаписи всех секретов (`kubectl replace`), и только после этого старый ключ удаляется из нижней части списка.

## 2. Блок 2. Практическое применение

### 2.1. Практика 1: Аудит безопасности через kube-bench и trivy

В данном практическом блоке разберем интеграцию автоматического аудита кластера и сканирования манифестов в DevSecOps-пайплайн.

#### Шаг 1. Запуск аудита CIS Benchmarks через kube-bench в кластере

Для автоматизированного сканирования Control Plane и Worker-нод запустим `kube-bench` в виде Kubernetes Job.

Создадим файл `kube-bench-job.yaml`:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: kube-bench-node-audit
  namespace: default
spec:
  template:
    metadata:
      labels:
        app: kube-bench
    spec:
      hostPID: true
      nodeSelector:
        node-role.kubernetes.io/control-plane: ""
      tolerations:
      - key: node-role.kubernetes.io/control-plane
        operator: Exists
        effect: NoSchedule
      containers:
      - name: kube-bench
        image: aquasec/kube-bench:v0.7.3
        command: ["kube-bench", "run", "--targets", "master,node,etcd"]
        volumeMounts:
        - name: var-lib-etcd
          mountPath: /var/lib/etcd
          readOnly: true
        - name: var-lib-kubelet
          mountPath: /var/lib/kubelet
          readOnly: true
        - name: etc-systemd
          mountPath: /etc/systemd
          readOnly: true
        - name: etc-kubernetes
          mountPath: /etc/kubernetes
          readOnly: true
      restartPolicy: Never
      volumes:
      - name: var-lib-etcd
        hostPath:
          path: /var/lib/etcd
      - name: var-lib-kubelet
        hostPath:
          path: /var/lib/kubelet
      - name: etc-systemd
        hostPath:
          path: /etc/systemd
      - name: etc-kubernetes
        hostPath:
          path: /etc/kubernetes

```

Выполнение аудита и просмотр результатов:

```bash
# Запуск Job в кластере
kubectl apply -f kube-bench-job.yaml

# Ожидание завершения сканирования
kubectl wait --for=condition=complete job/kube-bench-node-audit --timeout=60s

# Вывод детального отчета
kubectl logs job/kube-bench-node-audit

```

Запуск `kube-bench` напрямую на узлах через CLI:

```bash
# Запуск проверки компонента Control Plane
kube-bench run --targets master

# Запуск проверки Worker-ноды
kube-bench run --targets node

```

> [!note] Ключевые флаги kube-bench
> Флаг `hostPID: true` в манифесте Job обязателен, так как `kube-bench` должен инспектировать аргументы запущенных процессов `kube-apiserver`, `kubelet` и `etcd` на самом хосте.

#### Шаг 2. Сканирование образов и конфигураций с помощью Trivy

Утилита Trivy от Aqua Security используется для сканирования контейнерных образов на CVE и валидации YAML-манифестов на ошибки безопасности.

```bash
# 1. Сканирование контейнерного образа на критические и высокие уязвимости (CVE)
trivy image --severity CRITICAL,HIGH nginx:1.25.1

# 2. Сканирование локальных YAML-манифестов на ошибки SecurityContext и конфигураций
trivy config ./infrastructure-manifests/

# 3. Полный аудит запущенных ресурсов в кластере Kubernetes
trivy k8s --report summary cluster

```

### 2.2. Практика 2: Настройка шифрования секретов в etcd (EncryptionConfiguration)

Пошаговая процедура перевода хранилища etcd на шифрование без простоя Control Plane кластера (релевантно для экзамена CKS и Production-сред).

> [!danger] Обязательный бэкап перед изменением шифрования
> Любая ошибка в синтаксисе `/etc/kubernetes/enc/enc.yaml` или неверный путь к файлу приведет к тому, что API-сервер не сможет завестись. ПЕРЕД выполнением процедуры обязательно создайте снимок etcd (`etcdctl snapshot save`)!

#### Шаг 1. Генерация ключа и создание конфигурационного файла

Сгенерируем 32-байтовый случайно распределенный ключ, закодированный в base64:

```bash
# Генерация 32-байтового ключа
BASE64_KEY=$(head -c 32 /dev/urandom | base64)
echo "Generated Key: ${BASE64_KEY}"

# Создание директории для конфигурации шифрования на Master-ноде
sudo mkdir -p /etc/kubernetes/enc

```

Создадим файл `/etc/kubernetes/enc/enc.yaml`:

```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      - aead:
          keys:
            - name: key1
              secret: <ВСТАВЬТЕ_СГЕНЕРИРОВАННЫЙ_BASE64_КЛЮЧ>
      - identity: {}

```

#### Шаг 2. Модификация манифеста API-сервера

Отредактируем манифест статической Поды `/etc/kubernetes/manifests/kube-apiserver.yaml`.

Добавим флаг запуску `kube-apiserver`:

```yaml
spec:
  containers:
  - command:
    - kube-apiserver
    - --encryption-provider-config=/etc/kubernetes/enc/enc.yaml

```

Добавим монтирование директории с ключом в разделы `volumeMounts` и `volumes`:

```yaml
    volumeMounts:
    - mountPath: /etc/kubernetes/enc
      name: enc-cer
      readOnly: true
  volumes:
  - hostPath:
      path: /etc/kubernetes/enc
      type: DirectoryOrCreate
    name: enc-cer

```

После сохранения файла Kubelet автоматически перезапустит под `kube-apiserver`. Дождитесь восстановления работы API-сервера (`kubectl get pods -n kube-system`).

#### Шаг 3. Шифрование существующих секретов

Все секреты, созданные до включения `EncryptionConfiguration`, остаются в etcd в открытом (base64) виде. Для их принудительного зашифрования необходимо перезаписать все объекты Secret:

```bash
# Принудительное обновление всех секретов во всех пространствах имен
kubectl get secrets --all-namespaces -o json | kubectl replace -f -

```

#### Шаг 4. Прямая проверка etcd через etcdctl

Убедимся, что секрет действительно записан в зашифрованном виде. Создадим тестовый секрет и прочитаем его напрямую из etcd:

```bash
# Создание тестового секрета
kubectl create secret generic database-pass --from-literal=pass=SuperSecret123

# Запрос напрямую к etcd через etcdctl
ETCDCTL_API=3 etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  get /registry/secrets/default/database-pass | hexdump -C

```

Вывод команды должен содержать префикс `k8s:enc:aead:v1:key1`, подтверждающий шифрование:

```text
00000000  2f 72 65 67 69 73 74 72  79 2f 73 65 63 72 65 74  |/registry/secret|
00000010  73 2f 64 65 66 61 75 6c  74 2f 64 61 74 61 62 61  |s/default/databa|
00000020  73 65 2d 70 61 73 73 0a  6b 38 73 3a 65 6e 63 3a  |se-pass.k8s:enc:|
00000030  61 65 61 64 3a 76 31 3a  6b 65 79 31 3a 2d b7 1f  |aead:v1:key1:...|

```

### 2.3. Практика 3: Резервное копирование etcd и безопасная работа с секретами

Разберем низкоуровневое создание снимков etcd и безопасную доставку секретов из Vault через External Secrets Operator.

#### Шаг 1. Резервное копирование etcd (`etcdctl snapshot`)

Для создания снимка состояния базы данных etcd используется утилита `etcdctl` с передачей параметров PKI-аутентификации:

```bash
# Создание снимка базы данных etcd
ETCDCTL_API=3 etcdctl snapshot save /var/lib/etcd-snapshot-backup.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# Проверка валидности и статуса созданного снимка
ETCDCTL_API=3 etcdctl snapshot status /var/lib/etcd-snapshot-backup.db --write-out=table

```

Пример вывода статуса снимка:

```text
+----------+----------+------------+------------+
|   HASH   | REVISION | TOTAL KEYS | TOTAL SIZE |
+----------+----------+------------+------------+
| c3f8a10b |    15420 |       1245 |     3.1 MB |
+----------+----------+------------+------------+

```

> [!tip] Рекомендация CKS/CKA по путям сертификатов etcd
> На экзамене всегда проверяйте манифест `/etc/kubernetes/manifests/etcd.yaml`. Из него можно быстро скопировать точные пути к `--listen-client-urls`, `--trusted-ca-file`, `--cert-file` и `--key-file`, чтобы не допустить ошибок при выполнении `etcdctl snapshot save`.

#### Шаг 2. Безопасная работа с секретами через External Secrets Operator (ESO)

Вместо ручного создания секретов через `kubectl create secret` в Production используется декларативная подтяжка из Vault.

Пример манифеста `ExternalSecret`:

```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: vault-app-secrets
  namespace: default
spec:
  refreshInterval: "1h"
  secretStoreRef:
    name: vault-backend
    kind: SecretStore
  target:
    name: app-production-secret
    creationPolicy: Owner
  data:
  - secretKey: DB_PASSWORD
    remoteRef:
      key: secret/data/production/database
      property: password

```

Применение данного манифеста приводит к тому, что ESO автоматически запрашивает секрет из Vault и создает native Kubernetes Secret с именем `app-production-secret` и ключом `DB_PASSWORD`.
